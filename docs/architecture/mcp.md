# Remote MCP Server

The MCP server at `agents.releases.sh` (alias `mcp.releases.sh`) is how AI agents consume the registry directly — the same data the REST API serves, packaged as MCP tools an agent can call from Claude, Codex, Cursor, or any MCP client. It lives in `apps/mcp/`, built on the Agents SDK's `createMcpHandler` (`agents/mcp/server`) with Streamable HTTP transport — see [Transport](#transport) for the wire-level detail. Reading this doc, you mostly need three things: **what the tools are** (this section and the two below), **who can call what** ([Authentication & scope enforcement](#authentication--scope-enforcement)), and **how to add or change a tool** (register it in `createServer`, then keep the [WebMCP subset](#parity-with-webmcp) in sync).

The tool surface is mostly read-only, split across two groups — search (`search`, `get_latest_releases`, `get_release`, and the **beta** `whats_changed`) and registry detail (`list_catalog`, `get_catalog_entry`, `list_organizations`, `get_organization`, `lookup_domain`) — plus a small set of per-user/per-workspace tools that act on the caller's own account: **follows** (`follow`, `unfollow`, `list_follows`, `get_personalized_feed`) and **webhooks** (`list_webhooks`, `manage_webhook`). Alongside the tools it advertises MCP **resources** (`releases://org/...`, `releases://catalog/...`) for browseable access and **prompts** (`whats_new`, `compare_products`, `catch_me_up`) as priming entry points. Read tools are public — no token required. The privileged paths (the on-demand lookup inside `search`, the follows tools, the webhook tools) require auth; see [Per-user follows tools](#per-user-follows-tools) and [Per-user + per-workspace webhook tools](#per-user--per-workspace-webhook-tools).

**Catalog unification (issue #539):** `list_catalog` and `get_catalog_entry` treat products and standalone sources as one thing — a catalog entry — and fold them into a single list with an `entryType: "product" | "source"` discriminator. `search` is the unified entry point: it searches orgs, catalog, and releases in one call, and takes an optional `type: ("orgs" | "catalog" | "releases")[]` filter to skip sections (agents that only need registry lookups should pass `type: ["catalog"]` to avoid the vector-retrieval path). The `releases://catalog/{slug}` resource mirrors the tool shape; `releases://product/...` and `releases://source/...` stay for one cycle as deprecated aliases.

**Progressive detail (issue #556):** `get_organization` and `get_catalog_entry` follow a simple/expanded pattern. By default both return the lightweight view — `get_organization` shows a preview of the AI-generated overview (first paragraph), and `get_catalog_entry` for a source lists tracked CHANGELOG files by path and byte size. Pass `include_overview: true` on `get_organization` to inline the full briefing; pass `include_changelog: true` (or any of `changelog_path` / `changelog_offset` / `changelog_limit` / `changelog_tokens`) on `get_catalog_entry` to embed the CHANGELOG slice. Heading-aligned slicing supports per-package files (e.g. `packages/next/CHANGELOG.md`) and emits `totalTokens` / `sliceTokens` for LLM budgeting (recommended brackets: 2000 / 5000 / 10000 / 20000). This replaces the standalone `get_organization_overview`, `get_source`, and `get_source_changelog` tools.

**Release importance + `minImportance` (issue #2098):** `get_latest_releases` and `whats_changed` render the AI-scored `importance` field (1–5, `@buildinternet/releases-core/importance`'s `IMPORTANCE_MIN`–`IMPORTANCE_MAX`; 5 = landmark, 1 = housekeeping) inline as `Importance: N/5` — omitted entirely for a release with no score (`null`: unclassified history, a parser miss, or content predating the #2089 scoring pass). Both tools accept an optional `minImportance` that keeps only releases scored at or above the threshold; an unscored release never satisfies the filter, mirroring the REST `GET /v1/releases/latest?minImportance=` predicate (`importance >= ?`, which SQL-excludes `NULL`) exactly. `get_latest_releases` applies the filter in its own D1 query — the MCP worker reads D1 directly here, it doesn't proxy the REST route. `whats_changed` is different: it's a thin proxy to `GET /v1/whats-changed`, whose response doesn't carry `importance` at all, so the tool does a small follow-up D1 lookup keyed by `(source_id, version)` over the already-resolved entries to attach a score before rendering and filtering (see the doc comment in `apps/mcp/src/whats-changed-tool.ts`). Out-of-range or non-integer `minImportance` is rejected: the zod input schema bounds it to `IMPORTANCE_MIN`–`IMPORTANCE_MAX` so real MCP clients get a structured validation error for free, and both tools' exported functions re-validate defensively so direct (non-server) callers get the same model-readable rejection text. Deliberately not added to `get_collection_releases`, `search`, or `get_personalized_feed`. Neither tool is part of the WebMCP browser subset (see [Parity with WebMCP](#parity-with-webmcp)), so no provider change was needed; the release-feed MCP App UI round-trips `minImportance` transparently through its generic `{ ...inputs, cursor }` pagination continuation, with no UI code change required.

The worker binds to the same D1 database as the API worker and carries a service binding (`API`) to it so it can forward on-demand lookup calls without a round-trip through the public internet (see `"services": [{ "binding": "API", ... }]` in `apps/mcp/wrangler.jsonc`). `apps/mcp/` is excluded from root `workspaces` to avoid import conflicts.

## Transport

`apps/mcp/src/index.ts` serves both MCP wire eras from one `createServer` factory (`agents/mcp/server`'s `createMcpHandler`, invoked with `legacy: "stateless"` — the default), so the tool surface can't drift between them; a tool registered once is visible to both.

- **2026-07-28 (modern):** no `initialize` handshake. Each request carries its protocol version and client capabilities in reserved `_meta` keys (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`) alongside the standard `Mcp-Method` / `Mcp-Name` headers (SEP-2243); a request missing `Mcp-Method` is rejected with a `400`. Replies are **plain JSON** — `responseMode: "json"` governs this leg.
- **2025-era (legacy):** the classic `initialize` → `tools/*` flow keeps working, served statelessly from the same factory. Replies are **SSE-framed** (`event: message\ndata: {...}\n\n`), unchanged by this migration: `responseMode: "json"` only reaches the modern leg above — the SDK's legacy fallback constructs its own transport and always answers SSE regardless of that option — and `agents@0.17` (the handler this migration replaced) already returned `text/event-stream` on every response path, so there was no plain-JSON behavior on this leg to preserve. Clients no longer receive a session id, which costs nothing: `apps/mcp` binds no Durable Objects, so that id never guaranteed isolate affinity.

`tools/list`, `prompts/list`, and `resources/templates/list` carry `ttlMs: 3600000` / `cacheScope: "private"` on the top-level result envelope (`result.ttlMs` / `result.cacheScope`, not under `_meta`) — static per deploy, but auth-gated, because the caller's scopes decide which tools register. `resources/read` is uncached (live D1 reads).

`GET`/`DELETE /mcp` remain unserved — no listening stream, no session to close. `subscriptions/listen` is not implemented; that's [#346](https://github.com/buildinternet/releases/issues/346).

`route` and `allowedOriginHostnames` (passed to `createMcpHandler` in `index.ts`) must stay in sync with the deployed hostnames: the wrapper does its own route matching and Origin validation, and its defaults cover only localhost and `workers.dev` — a custom domain relies on Cloudflare routing unless it's named here.

## Per-user follows tools

`follow`, `unfollow`, `list_follows`, and `get_personalized_feed` (`apps/mcp/src/follows-tools.ts`, #1520) act on the **caller's own account**, unlike every other tool (read-only against the shared registry). They don't touch D1 directly — they proxy through the API worker's `/v1/me/*` routes over the `API` service binding, forwarding the caller's own Bearer credential so the API resolves and acts as the user. The MCP server never holds a user id; the API is the source of truth.

This requires a **user** principal. The HTTP boundary (`apps/mcp/src/auth.ts`) carries the raw credential on `McpIdentity.userToken` for exactly the two user lanes — a `relu_` user key or a "Sign in with Releases" OAuth JWT — and null for anonymous / machine (`relk_`) / root callers. `userToken` is deliberately distinct from `token` (the on-demand-lookup credential, which stays null for user lanes so that lookup falls back to the root key rather than re-metering the user key). When `userToken` is null the follows tools return an actionable error rather than calling the API. `follow`/`unfollow` take an `org_…`/`prod_…` typed id (the target type is inferred from the prefix) so the LLM passes ids straight from `search` / `get_*` results; they're not scope-gated (a read-only `relu_` key manages its owner's follows). Note: a `relu_`-authed follow call meters the key twice — once at MCP identity resolution (`GET /v1/tokens/me`) and once at the forwarded `/v1/me/*` operation; the OAuth-JWT lane verifies locally both times and meters neither.

## Per-user + per-workspace webhook tools

`list_webhooks` and `manage_webhook` (`apps/mcp/src/webhook-tools.ts`, [#1678](https://github.com/buildinternet/releases/issues/1678) / [#2326](https://github.com/buildinternet/releases/issues/2326)) cover both self-serve outbound webhook surfaces — personal (`/v1/me/webhooks`) and workspace (`/v1/workspaces/:workspaceId/webhooks`) — in one tool design instead of two parallel sets. Like the follows tools, they act on the caller's account and proxy to the API worker over the `API` service binding, forwarding `McpIdentity.userToken`. Same gate as follows: a `relu_` user key or an OAuth JWT resolves to a user; anonymous, machine (`relk_`), and root callers get the same actionable error instead of a call. There's no catalog `write` scope requirement — a read-only `relu_` key can still manage the webhooks it owns, and a workspace's role decides what a member may do.

**Two tools, not one**, so the MCP tool annotations stay honest: `list_webhooks` is read-only; `manage_webhook` covers `create` / `update` / `delete` / `test` / `rotate_secret` behind one `action` enum and is marked `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true` (it ships to an external URL the caller supplies). Both tools take an optional `workspace` (an id or a slug) — omit it for the caller's personal webhooks, or pass one to target that workspace's webhooks instead. A `scope: "follows"` webhook is personal-only; passing it together with `workspace` is rejected before any API call.

**Finding a workspace id:** `GET /v1/me/workspaces` (#2327) lists the caller's workspaces — id, slug, role. `list_webhooks` calls it and appends a short list to its output whenever `workspace` is omitted, so an agent can discover a workspace id from the same call it'd make anyway; the section is silently omitted if that lookup fails. `workspace` resolution (`resolveWorkspace` in `webhook-tools.ts`) matches the input against the caller's own workspaces — exact id first, then exact slug — and a miss returns an error listing the caller's workspaces rather than a raw 404, since the API itself never exposes a lookup-by-arbitrary-id endpoint.

**Status mapping:** once a `workspace` resolves, membership is already confirmed, so a subsequent `403` from a workspace webhook route becomes "Only workspace owners and admins can change workspace webhooks." and a `404` on a `:id` route becomes "Webhook not found in this workspace." A personal-route `404` is just "Webhook not found." A `429` on `test` (the per-subscription/per-user test-delivery rate limit) surfaces the API's message plus a retry hint. Everything else renders the API's own error message.

**Signing keys:** `create` and `rotate_secret` return a one-time `signingKey` for `json`-format webhooks — the tool response says it's shown once and must be stored now. `slack` and `discord` deliveries aren't HMAC-signed, so those formats say so instead of a key.

**On-demand lookup fallback (issues #611, #662, #664):** When `search` returns no entity hits (orgs / catalog) and the query parses as a `{org}/{repo}` GitHub coordinate — optionally prefixed `github:` — the tool calls `POST /v1/lookups` via the `API` service binding before returning. The gate intentionally ignores release / chunk hits: those routinely fire on a single segment token (e.g. "shopify" matching another org's release body) and would otherwise suppress the lookup for the typed repo. The lookup result is merged under a `lookup` field in the tool response (`status`, `source`, `releases`, `relatedOrg`). Five outcomes: `indexed` (new source materialized), `existing` (already tracked — matched case-insensitively against `sources.url`, so `shopify/toxiproxy` and `Shopify/Toxiproxy` resolve to the same row), `empty` (repo exists but has no releases/CHANGELOG), `not_found` (404/403/archived), `deferred` (GitHub rate-limit or 5xx — transient, no negative cache written). The `lookup` field is `null` when no coordinate was detected or when an entity match was already returned. The on-demand lookup is also suppressed when `search` is called with a `domain` filter — the caller has already named an entity.

**Domain lookup (`lookup_domain`):** Given a URL-shaped input, normalize it via `normalizeDomain` (`@buildinternet/releases-core/domain`) and exact-match against `organizations.domain` (primary) and `domain_aliases.domain` (alias for either an org or a product). Returns the matched org plus any products whose alias targets the same domain. On a complete miss the API may just-in-time materialize a stub from `/.well-known/releases.json` when listing is enabled (#2030) — same behavior as `GET /v1/lookups/by-domain`. Unknown domains with no valid manifest still surface a "no match" message. The same normalizer powers the `domain` input on `search`, which scopes a query to the resolved org (and short-circuits with empty arrays + a "no match" hint when the domain isn't owned).

Deploy: `bun run deploy:mcp`. Dev: `bun run dev:mcp`. Connect from Claude Desktop: `npx mcp-remote https://agents.releases.sh/mcp`.

## Authentication & scope enforcement

Scoped API tokens (Phase 2 of the [scoped API tokens design](../superpowers/specs/2026-05-20-scoped-api-tokens-design.md)) are enforced here. `apps/mcp/src/auth.ts` resolves the caller's identity once per request, **at the HTTP boundary** in `index.ts` — `createMcpHandler` doesn't expose the inbound `Authorization` header to tool handlers, so the boundary is the only place to read it. Identity (scopes + the raw token) is threaded into `createServer` via `CreateServerOptions`, the same mechanism that carries `userAgent`.

**Identity resolution** (`resolveMcpAuth`, mirroring the API worker's `resolveAuth`):

- A `relk_…` Bearer is verified against D1 via the shared `verifyApiToken` from `@releases/core-internal/api-token-store` — one verification path for both workers. On success the caller carries the token's scopes; an invalid/unknown `relk_` token is **ignored** (resolves to anonymous read) so public reads never 401, exactly like the API worker's public-read path. Gated by `API_TOKENS_DISABLED`.
- A `relu_…` Bearer (Better Auth user key) is verified by authenticating it against the API worker's `GET /v1/tokens/me` over the `API` service binding — the MCP worker never instantiates Better Auth. The API worker's middleware verifies **and meters** the key exactly once and returns its scopes. Metering is gated on a JSON-RPC method peek (`isMeteredMcpMethod`): only billable methods (`tools/call`, and anything not in the protocol-overhead allowlist) trigger the verify; `initialize`/`tools/list`/`ping`/`notifications/*`/etc. resolve to anonymous and are never metered. A `429` from `/v1/tokens/me` surfaces as a `429` from the boundary; an invalid key, an unreachable binding, the flag being off, or any error fail-open to anonymous read. Gated by `user-api-keys-enabled` (and `API_TOKENS_DISABLED`); inert in prod until Phase 3.
- A JWT-shaped Bearer is treated as a "Sign in with Releases" OAuth access token (#1483) and verified locally with `jose` + the AS JWKS via the shared `@releases/lib/oauth-jwt` (the MCP worker never imports better-auth — zod-pin). A verified token carries the `scope`-claim scopes (already role-clamped at issuance) under a `oauth_<sub>` tokenId with `token: null`. Unlike the `relk_`/`relu_` lanes, a presented-but-**invalid** JWT (bad signature, wrong `iss`/`aud`, expired, or zero API scopes) does **not** fall open to anonymous — it returns a `401` + `WWW-Authenticate` discovery challenge (see [OAuth discovery surface](#oauth-discovery-surface-rfc-9728)). Issuer/audience come from `OAUTH_JWT_ISSUER`/`OAUTH_JWT_AUDIENCE` (prod defaults shared with `well-known.ts`).
- The static `RELEASES_API_KEY` presented as Bearer maps to **root** (`["*"]`).
- Anything else (**no credential**) is **anonymous**, carrying an implicit `["read"]` scope — public read is never gated.

A successful `relk_` token use records `last_used_at` via `touchLastUsed` (throttled to 60s, fire-and-forget through `waitUntil`) so the admin surface audits usage across both workers. `relu_` user keys are metered by Better Auth's `apikey` table instead, so the machine-lane write is skipped for them (`machineTokenIdForUsage`).

**Per-tool scope map:**

| Tools                                                                                            | Required scope                                                                                       |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| All read tools (`search`, `get_*`, `list_*`, `lookup_domain`)                                    | none (open to anonymous `read`)                                                                      |
| The on-demand `/v1/lookups` fallback inside `search`                                             | `write`                                                                                              |
| `follow`, `unfollow`, `list_follows`, `get_personalized_feed`, `list_webhooks`, `manage_webhook` | a signed-in USER (`relu_` key or OAuth JWT) — not a scope; see the anonymous sign-in challenge below |

The on-demand lookup gates inline (`scopeSatisfies(authScopes, "write")` in `mcp-agent.ts`): an under-scoped caller still gets normal `search` results — the GitHub materialization is simply skipped, no `lookup` rail is appended, and no error is surfaced. Note: user (`relu_`) keys are capped at read (`USER_API_KEY_MAX_SCOPE`), so they can never satisfy `write` and are therefore permanently excluded from the on-demand lookup — only `relk_` write/admin tokens and root reach it.

**Confused-deputy fix:** the on-demand lookup (`maybeLookup`) materializes a hidden source — a write. It previously presented the static root key on every call, so any MCP client borrowed root downstream. It now fires only when the caller's scopes satisfy `write`, and forwards the **caller's own** `relk_` token to `POST /v1/lookups` (a static-root caller forwards root — root acting as root). Anonymous/read callers no longer trigger the lookup at all. **Behavior change:** on-demand GitHub indexing via the public MCP now requires a `write`-scoped token rather than silently running as root for everyone. For a `relu_` caller the identity carries `token: null`, so `maybeLookup` forwards the **root** key (its `authToken ?? rootKey` fallback) rather than the user key — the inbound tool call is already metered once at the boundary, and forwarding the user key would double-count it at `/v1/lookups`. Note: under the current read-only ceiling (`USER_API_KEY_MAX_SCOPE = "read"`) a `relu_` key's scopes are clamped to read at auth time, so it can never satisfy this `write` gate — `maybeLookup` never fires for a user key at all, and the forwarding-root path above only becomes reachable if that ceiling is later raised.

**Staging gate bridge:** the staging access gate (`STAGING_ACCESS_KEY`, staging only) runs in the same `resolveMcpAuth` pass. It still accepts the `X-Releases-Staging-Key` header and `Authorization: Bearer <staging-key>`, and now **also** accepts a valid staging-DB `relk_` token (or the root key) — so an Anthropic managed agent, whose vault credentials are Bearer-only, can authenticate to `mcp-staging` with a token instead of the shared staging key. A `relu_` user identity does **not** open the gate (it carries `token: null`; the bridge requires `identity.token !== null`), so a user key must still supply the staging key in staging. CORS preflight (`OPTIONS`) always passes.

## OAuth discovery surface (RFC 9728)

The MCP authorization spec (2025-06-18) requires an MCP server, acting as an OAuth 2.1 resource server, to advertise its authorization server so a client can discover where to authenticate and what `resource` (RFC 8707) to request. The better-auth AS only mints a JWT (rather than an opaque token) when the client sends `resource` on the token request — so without this discovery surface the JWT lane above never engages for an off-the-shelf client. `apps/mcp/src/well-known.ts` provides it:

- **`GET /.well-known/oauth-protected-resource`** (and the RFC 9728 §3.1 path-suffixed `…/oauth-protected-resource/mcp`) returns the protected-resource metadata: `{ resource, authorization_servers, scopes_supported, bearer_methods_supported }`. `resource` is the configured audience on the host the request came in on (`OAUTH_JWT_AUDIENCE` is a comma list of bare origins — prod: `https://agents.releases.sh, https://mcp.releases.sh` — and the first is the fallback for any other host), so RFC 9728's "resource must match the URL used" check passes on both hosts; `authorization_servers` is `[OAUTH_JWT_ISSUER]` (`https://api.releases.sh/api/auth`), from which the client does RFC 8414 AS-metadata discovery. The AS and this worker accept every listed origin plus its `/mcp` transport URL as RFC 8707 `resource` / JWT `aud` so clients that copy either host or the transport URL still complete OAuth (see [mcp-cimd-interop.md](mcp-cimd-interop.md)). Discovery keeps advertising the origin. In prod it is public discovery, short-circuited **before** `resolveMcpAuth` (like `/robots.txt`); on staging it is deferred until **after** the staging access gate so it stays opaque like every other route (a harness already carries the staging key).
- **`WWW-Authenticate` challenge (invalid token):** a presented-but-invalid OAuth JWT returns `401` with `WWW-Authenticate: Bearer error="invalid_token", resource_metadata="<origin>/.well-known/oauth-protected-resource"`, pointing the client at the metadata to re-authenticate. On staging the access gate runs first (`resolveMcpAuth`), so an invalid credential without the staging key gets the generic staging `401` rather than the discovery hint.
- **Anonymous sign-in step-up challenge (#2408):** the follows tools (`follow`, `unfollow`, `list_follows`, `get_personalized_feed`) and the webhook tools (`list_webhooks`, `manage_webhook`) act on the caller's own account and require a signed-in user — their tool names are the single source of truth in `USER_REQUIRED_TOOLS` (`apps/mcp/src/user-required-tools.ts`). Before this, a caller with no credential at all invoking one of them fell through to anonymous read and got back a plain tool-result error telling the model to present an API key; nothing prompted sign-in, so an OAuth-aware MCP client (Claude, et al.) never showed a sign-in flow. `resolveMcpAuth` now peeks the JSON-RPC body (reusing the same clone-and-parse approach as `isMeteredMcpMethod`) for a `tools/call` naming one of these tools; if the caller presented **no** `Authorization` header at all, it returns `401` with `WWW-Authenticate: Bearer scope="read", resource_metadata="<origin>/.well-known/oauth-protected-resource"` — no `error=` param, per RFC 6750 §3.1, since the token is absent rather than invalid (`missingTokenChallenge` in `well-known.ts`, the sibling of `wwwAuthenticateChallenge`). A JSON-RPC batch is challenged if ANY element targets a user-required tool; an unparseable body never challenges. This only fires for the genuinely credential-less lane: a `relk_`/`relu_`/root caller — even one whose token failed to verify and fell open to anonymous — keeps the existing tool-result `userRequired()` text (`follows-tools.ts` / `webhook-tools.ts`, via the shared implementation in `lib/user-api-proxy.ts`, which now also names the connector-settings sign-in path and throws if called for a tool missing from `USER_REQUIRED_TOOLS`). `initialize`, `tools/list`, notifications, and every read tool are unaffected. The staging access gate still runs first, same ordering as the invalid-JWT challenge above.

**Deliberate stance — anonymous read is preserved.** The MCP server is a public changelog registry, so this is _not_ a fully-protected resource: a **tokenless** request still resolves to anonymous `read` and never receives a 401 for a read tool, `initialize`, or `tools/list`. Only a request that presents an invalid OAuth credential, or a credential-less request targeting a user-gated tool, is challenged. This intentionally diverges from the spec's "401 on any tokenless connect" model, which would break public read.

The REST API worker is also an OAuth resource server and serves its own RFC 9728 metadata at `api.releases.sh/.well-known/oauth-protected-resource` (`resource` = the API origin); see [remote-mode.md → Auth model](remote-mode.md#auth-model). Its server-to-server JWKS fetch is why the staging access gate exempts `/api/auth/jwks`.

## MCP App UIs (`apps/mcp/ui/`)

Hosts that support the MCP Apps extension (Claude Desktop is the first) render a tool's response as an interactive UI when the tool advertises `_meta.ui.resourceUri`. Each UI is a single self-contained HTML resource registered alongside the existing entity resources. Hosts without UI support fall back to the markdown text in `content[0].text`, so every UI-enabled tool keeps its text rendering intact.

**Live surfaces:**

- `get_latest_releases`, `get_collection_releases` → `ui://releases/release-feed.html` (card timeline with cursor-based "Load more", "Open source", and "Ask about this").

**Build pattern (Bun, no Vite):** Each app lives in its own folder under `apps/mcp/ui/` with an `app.tsx` entry and a `styles.css`. `apps/mcp/ui/build.ts` runs `Bun.build` over the entry, reads the sibling CSS, inlines both into a minimal HTML shell, and writes the bundled strings into `apps/mcp/src/ui-bundles.ts`. The worker imports those strings and serves them through `registerAppResource` in `apps/mcp/src/resources.ts`. The bundle file is committed so deploys never depend on a UI install; `deploy:mcp` regenerates it first as a safety net.

**Adding a new UI:**

1. `mkdir apps/mcp/ui/<name>` and drop in `app.tsx` (React entry) + `styles.css`.
2. Add an entry to the `APPS` array in `apps/mcp/ui/build.ts`.
3. Add an exported URI constant + `registerAppResource` call in `apps/mcp/src/resources.ts`.
4. On the tool registration, add `_meta: { ui: { resourceUri: <CONST> } }`.
5. Have the tool's handler also return `structuredContent` with the typed payload the UI reads (see `ReleaseFeedStructured` in `apps/mcp/src/tools.ts` for the shape).
6. `bun run mcp:ui:build` to regenerate the bundle.

**Aliases:**

- `bun run mcp:ui:build` — production bundle, commits-clean
- `bun run mcp:ui:build:dev` — inline source maps + unminified for debugging
- `bun run mcp:ui:watch` — rebuild on save during UI iteration
- `bun run mcp:ui:typecheck` — `tsc --noEmit` over the UI tree

**Data contract:** UI-enabled tools attach `structuredContent` to their result. The UI consumes that field directly via `app.ontoolresult`; the model still reads the markdown `content[0].text`. Cursor pagination from the UI is wired through `app.callServerTool({ name, arguments: { ...inputs, cursor } })` — no host re-prompt needed to extend the feed.

**Vite note:** the MCP Apps SDK's React template ships with Vite + `vite-plugin-singlefile`. We don't use Vite — Bun's bundler produces the same single-file output via a ~30-line build script. The `@modelcontextprotocol/ext-apps` package is consumed only by UI code (for `useApp` and types); the worker doesn't depend on it at runtime, so worker deploys stay lean.

## Spec utilities

- **Ping (`ping`):** supported transparently. The SDK's base `Protocol` class registers a default handler that responds with `{}`, so every server instance ships it without code.
- **Tool annotations:** every read tool carries `readOnlyHint: true, destructiveHint: false, openWorldHint: false, idempotentHint: true` plus a display `title`. The per-user mutation tools `follow` and `unfollow` instead set `readOnlyHint: false` (they write the caller's follows) while keeping `destructiveHint: false`, `openWorldHint: false`, and `idempotentHint: true` (re-following / re-unfollowing is a no-op). The hints are asserted in `apps/mcp/test/mcp-tool-annotations.test.ts` so regressions fail fast.
- **Identifiers — IDs alongside slugs:** every tool, prompt, and resource that takes an org / product / source identifier accepts a typed ID (`org_…`, `prod_…`, `src_…`) interchangeably with the slug or `org/slug` coordinate form. Releases are different — `get_release` accepts only `rel_…` or a bare 21-char nanoid, never a slug. Tool descriptions explicitly list each shape. The bare-slug path on `releases://catalog/{slug}` and `releases://org/{orgSlug}` still works, but the URI segment also resolves a typed ID — completion only offers slugs because IDs aren't browseable. `findOrg` (`apps/mcp/src/tools.ts`) folds the `org_…` PK match into the existing UNION query as an additional `OR` predicate, so the indexed PK hit is a fast-path within the same statement that handles slug / domain / domain-alias / account-handle resolution. The catalog and product helpers branch on `getEntityType` to dispatch to the correct lookup. Prefer IDs in agent prompts where stability matters more than readability.
- **Resources + completion:** `apps/mcp/src/resources.ts` registers four templates — `releases://org/{orgSlug}`, `releases://catalog/{slug}`, and the deprecated-alias pair `releases://product/{productSlug}` + `releases://source/{sourceSlug}`. All four are completion-only (no `resources/list` enumeration) — the SDK doesn't thread a cursor through `listCallback`, so capping or alphabetizing would silently hide rows as the catalog grows. Completion (in `apps/mcp/src/slug-completion.ts`) runs case-insensitive substring LIKE against both the slug and the display name, ranks prefix matches ahead of mid-string matches, sanitizes user input (`%`/`_`), and returns up to 20 candidates. **Org completion returns bare slugs** because `organizations.slug` is still globally unique. **Catalog (product + source) completion returns `org/slug` coordinates** instead of bare slugs because per-org slug uniqueness (#690) means a bare slug isn't an unambiguous handle, and downstream tools (`get_latest_releases`, `get_catalog_entry`) reject bare slugs with a 400 — coordinates round-trip cleanly. Typed IDs are not surfaced through completion — they're not memorable, but URI handlers and tool inputs accept them directly. `completeCatalogSlug` fans out to the product and source completers in parallel and de-dupes on collision. Substring LIKE forces a table scan but the tables are low-thousands of rows — revisit with FTS5 if the catalog grows by 100×. Read callbacks delegate to `getOrganization`/`getCatalogEntry`/`getProduct` and return `text/markdown`; the deprecated source-resource route is folded into `getCatalogEntry` under the hood.
- **Prompts:** `apps/mcp/src/prompts.ts` registers three priming prompts — `whats_new`, `compare_products`, `catch_me_up`. `whats_new` and `compare_products` accept a `prod_…` id or `org/slug` coordinate (completion returns coordinates so the interpolated tool call is accepted); `catch_me_up` accepts an org\_ id, slug, domain, name, or account handle. Prompts emit a single user message that names the exact tools the LLM should call (so models that don't auto-plan still land on the right entry points). `whats_new` and `compare_products` both instruct the LLM to call `get_latest_releases` and synthesize the summary/comparison itself. Completion for both resources and prompts reuses `apps/mcp/src/slug-completion.ts`.

## Parity with WebMCP

The web app also exposes a browser-side subset of these tools via `navigator.modelContext.registerTool()` — see `apps/web/src/components/webmcp-provider.tsx`. Today that surface mirrors `search`, `lookup_domain`, `list_organizations`, `get_organization`, `get_catalog_entry`, `get_release` plus an `open_search_page` nav helper, all pointed at the public API. WebMCP is intentionally a lightweight subset — it does not mirror resources or prompts, and it is not expected to track remote-MCP surface additions 1:1. When you add, rename, or change the signature of a read-only tool in `apps/mcp/src/tools.ts`, update the WebMCP provider in the same PR so the tool subset doesn't drift. The OSS CLI's stdio bridge (`releases admin mcp serve`) is a thin proxy to the hosted server, so it inherits tool changes on the next worker deploy. Write/admin tools stay out of WebMCP — browser-side callers can't present an API key safely.

## MCP Registry listing

The server is registered as `sh.releases/mcp` in the official MCP Registry via HTTP-domain auth against `releases.sh` (proof file lives at `apps/web/public/.well-known/mcp-registry-auth`). Metadata is in `apps/mcp/server.json` — bump `version` when you want to publish an update.

**Which version is authoritative:** three separate numbers exist, and only two are meant to agree. `server.json`'s `version` is registry metadata, and it must match the `version` the server advertises in `createServer`'s `McpServer` constructor (`apps/mcp/src/mcp-agent.ts`) — that is what clients actually see on connect, so a mismatch publishes stale metadata. `apps/mcp/package.json`'s `version` is **not** a source of truth for either: the worker is `private: true` and never published to npm, so that field is inert and has drifted behind. Bump `server.json` and the `McpServer` constructor together; leave `package.json` alone. The `Deploy Workers` GitHub Action runs `mcp-publisher publish` automatically on merges that touch `server.json` (gated on the `MCP_REGISTRY_PRIVATE_KEY_PEM` repo secret). Manual publish: `bun run publish:mcp-registry` after `mcp-publisher login http --domain releases.sh --private-key <hex>`. `serverInfo.icons` is independent of the version bump and points at `https://releases.sh/icon.svg`.
